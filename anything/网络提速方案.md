# 网络提速方案：HuggingFace 下载 + 微信传文件

> 现场体检时间：2026-10-17 22:45，本机（macOS 26.5.1 / Apple Silicon）

## 0. 一句话结论

**你的宽带没问题，问题是「所有流量都被全局 TUN 代理押送到日本大阪的一个节点上，包括访问国内站点」。**
这个节点下行 ~0.5–1.5 MB/s、上行只有 ~28 KB/s。所以不只是 HF 慢，连清华镜像、微信上传都跟着一起被拖死。

## 2. 根因排序

1. **【决定性】全局代理 + 慢节点。** 证据是「清华镜像只有 55 KB/s」——国内镜像本该跑满带宽，唯一的解释就是它也被绕到日本去了。你不是"网速慢"，是"所有流量都在过一根 1.5MB/s 的管子里"。
2. **【次要】WiFi 卡在 2.4GHz。** 你这台 Mac 连的是 2.4G 频道 1、20MHz，同频道还有 -47dBm 的邻居 AP 在抢。附近明明有 5GHz（ch153 / 80MHz）可用，速率能差 3–5 倍。
3. **【工具】单线程直连 + 浏览器下载。** 实测 HF 单线程 470 KB/s，aria2 8 连接 1.5 MB/s，**差 3 倍**，这部分不用改网络就能白拿。
4. **【空间】只剩 12 GB。** 再下个大模型直接爆盘，下到一半失败最难受。

## 3. 按收益排序的 5 个动作

### 动作 1（收益最大，一次配置管所有场景）：打开分流

已经给你写好了两个可直接粘贴的文件：

- Quantumult X → `qx-rules.conf`（`host-suffix` / `geoip` 语法，粘到配置的 `[filter_local]` 段最前面）
- Shadowrocket → `shadowrocket-rules.conf`（`DOMAIN-SUFFIX` / `GEOIP` 语法，粘到 `[Rule]` 段最前面）

核心只有一行 **`GEOIP,CN,DIRECT`**（QX 写 `geoip, cn, direct`）：国外依然走代理，国内全部直连。

| 规则 | 作用 |
|---|---|
| `DOMAIN-SUFFIX,huggingface.co,PROXY` | HF 本体和 LFS 走代理（被墙，必须走） |
| `GEOIP,CN,DIRECT` | 清华/阿里/腾讯/微信/百度… 全部直连 |
| `FINAL,PROXY` | 其余照旧走代理 |

三个注意点：

1. 规则顺序：**域名规则在前，`GEOIP,CN,DIRECT` 在后，`FINAL` 最后**。
2. 如果你的策略不叫 `PROXY` 而是自定义策略组（比如「国外流量」），把 `PROXY` 换成组名。
3. **改完必须重启正在跑的下载**——老连接不会自动切线路。

改完后国内镜像应该立刻从 55 KB/s 跳到 5–11 MB/s（100M 宽带上限）。

### 动作 2（现在就能用，不用改任何设置）：换成多线程下载

本目录的 `hfget.sh` 已经把 aria2 的参数调好了（**8 连接**，实测比 16 连接更快）：

```bash
./hfget.sh Qwen/Qwen2.5-7B-Instruct --dir ~/models      # 整个仓库，断点续传
./hfget.sh openai-community/gpt2 "*.safetensors"        # 只要某类文件
./hfget.sh --list Qwen/Qwen2.5-7B-Instruct              # 先看清单和体积
```

你要是继续用手写的 aria2 命令，把 `-x16` 改成 `-x8`：这个节点上 16 连接会互相挤，平均只有 834 KB/s，8 连接能到 1.5 MB/s。

### 动作 3（配合动作 1 才有意义）：走国内镜像

分流生效后，走 hf-mirror 会更快：

```bash
./hfget.sh --mirror Qwen/Qwen2.5-7B-Instruct --dir ~/models
# 或给 hf 命令行 / 其它工具设：
export HF_ENDPOINT=https://hf-mirror.com
```

⚠️ 顺序不能反：**现在还没分流，hf-mirror 反而更慢**（实测 101 KB/s，因为也被绕到日本）。所以先做动作 1。

另外别用 `huggingface_hub 2.x` 的 `hf download` + `hf_transfer`：新版已经废弃 hf_transfer、改用 Xet，在这条线路上会卡在 0 字节不动（我这边实测 45 秒下一个字节都没下来）。

### 动作 4：WiFi 换 5GHz

- 系统设置 → Wi-Fi → 连你路由器的 **5G** SSID（扫描到的是 ch153、80MHz、802.11a/n/ac）。
- 路由器里可以把 2.4G 和 5G 的 SSID 改成不同名字，避免 Mac 一直赖在 2.4G。
- 有网口/扩展坞就直接插网线，比 WiFi 稳。

### 动作 5：腾磁盘

12 GB 不够用（7B ≈ 15GB、13B ≈ 26GB）。按收益清：

```bash
du -sh ~/Library/Caches/huggingface ~/Library/Caches/Homebrew ~/Library/Caches/pip 2>/dev/null
rm -rf ~/Library/Caches/huggingface/hub/*        # 旧模型缓存（会重下，慎用）
brew cleanup --prune=all
docker system prune -a                            # 有 Docker 的话
```

## 4. 微信传文件（重点）

### 4.1 先说现状：这台 Mac 根本没装微信

`/Applications` 里 24 个 App，没有 WeChat；也没有微信进程在跑。所以"传到文件传输助手"目前只能走手机，或者先装客户端。

- 官方下载：<https://mac.weixin.qq.com/>（国内 CDN，分流后几十秒就下完）

### 4.2 为什么现在传文件会非常痛苦

微信文件传输助手本身不限速，但**上传走的是你的上行**。你现在经日本节点上行只有 **28 KB/s**：

| 文件大小 | 现在（28 KB/s） | 分流后（按 20 Mbps 上行） |
|---|---|---|
| 10 MB | 6 分钟 | 4 秒 |
| 100 MB | **1 小时** | 40 秒 |
| 1 GB | 10 小时 | 7 分钟 |

所以**先修分流，再谈传文件**。这一条比换任何工具都管用。

### 4.3 微信自身的限制

- 单文件上限：**电脑端约 1 GB、手机端约 100 MB**（不同版本有差异，以客户端提示为准）；文件夹要先压缩成 zip。
- 微信对图片/视频会二次压缩，**发文件（"以文件形式发送"）不会被压**。
- 大文件（>1GB）别走微信，用下面的方案。

### 4.4 三个更快的替代方案（按场景选）

**① AirDrop（Mac → iPhone，最省事）**
两台设备同 WiFi、蓝牙开着，`右键文件 → 共享 → 隔空投送`。走的是局域网直连，30–80 MB/s，10 秒传完 1GB。到了手机上再从「文件」里转发给文件传输助手（手机上传走家里 WiFi/5G，通常比 Mac 经代理快得多）。

**② 局域网 HTTP（零安装，最通用）**
```bash
./lanshare.sh ~/Downloads        # 会打印 http://192.168.31.49:8000
```
手机连同一个 WiFi，Safari 打开那个地址 → 点文件下载 → 「文件」App 里长按 → 共享 → 微信 → 文件传输助手。速度就是 WiFi 上限（20–50 MB/s）。

**③ LocalSend（跨平台、可断点、无大小限制）**
```bash
brew install --cask localsend
```
Mac 和手机都装，同一个 WiFi 下互传，不经过任何服务器。

## 5. 改完之后怎么验收

再跑一次体检，对着这几个数看：

```bash
./net-doctor.sh
```

| 指标 | 现在 | 目标 |
|---|---|---|
| 清华镜像 单线程 | 55 KB/s | **5 MB/s 以上** ← 分流成功的铁证 |
| hf-mirror 单线程 | 101 KB/s | 5 MB/s 以上 |
| HuggingFace（aria2 ×8） | 1.5 MB/s | 3 MB/s 以上（取决于节点） |
| WiFi | 802.11n / 2.4GHz | 802.11ac / 5GHz / 80MHz |
| 上行 | 28 KB/s | 1 MB/s 以上 |

如果分流做了、清华镜像还是几百 KB/s，那就是节点在限速或运营商问题，换个节点再测。
